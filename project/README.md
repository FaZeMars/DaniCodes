# BlueApp

BlueApp is an application for exploring exchange rates used in Argentina. It brings currency information, conversion estimates, and three financial calculators into one menu. This project uses functions, dictionaries, loops, exceptions and HTTP requests.

In this project there is three main functions: Real-time value of currencies viewer function; a currency conversion function, which can convert from 8 different currencies; and lastly a financial calculators submenu, which shows 3 types of calculators, an savings calculator, an exchange rate gap calculator and an spread calculator.

The currency viewer retrieves data from DolarApi and displays buying and selling prices. Available options include the official, blue, MEP, card, and crypto dollar rates, plus the euro, Brazilian real, Chilean peso and Uruguayan peso. It also converts the API's update timestamp into a message showing how many minutes have passed since the last update. Missing or invalid timestamps appear as "Unknown"

The conversion function asks for a starting currrency, a target currency, and an amount. It estimates the result by multiplying the amount by the starting currency's buying price in Argentine pesos (ARS), then dividing by the target currency's selling price. The displayed unit rate uses six decimal places so small values still remain visible. Results are estimates based on published prices, requested from DolarApi, and do not include fees or guarantee that a certain exchange is available.

The financial calculators solve three different problems. The savings calculator compares the estimated peso cost of a USD amount using the card and MEP selling rates. The exchange rate gap calculator compares a selected dollar selling rate with the official selling rate, showing both the peso difference and its percentage. Lastly, the spread calculator substracts the buying price from the selling price and expresses that difference as a percentage of the selling price.

Regarding what files are in my project, project.py contains the whole application. Menu definitions are stored near the beginning as lists of dictio naries. main( ) starts the menu loop, while routing functions open the selected function. get_rate() handles API requests , iso_format_converter() handles timestamps, and validation functions check user amounts and exchange rates. Calculation functions perform the arithmetic, and separate display functions format the results. The file runs the application only when executed directly, allowing its functions to be used in other programs.test_project.py contains the unitary test for the main functions of BlueApp, and README.md (this file) explains this project. Lastly, there is a requirements.txt file that includes all the external libraries I used for the project.

Choosing how to design this project was initially hard for me. I began by writing very extense functions that combined objectives such as displaying, error checking and calculating, because that was what I thought was better for my project. I kept doing this until I noticed it was very hard to reuse functions in my programs for other purposes, as they were designed only around a certain purpose, so I had two choices. One was to redo the whole project and start off a blank page, and the second option was separating the functions I already had. It took me more than a day to decide what option to go for, as I believed starting off freshly would be easier than separating functions because I thought separating functions would confuse me a lot. Eventually, I decided to split functions because I thought that if everytime I did something wrong I'd redo it, I wouldn't really learn anything, so splitting functions really helped me thing more critically.

Another thing that was very hard for me whilst doing the project was figuring out how to store each of the different menu options and how to call each function without making a mess of a code. Obviously, I started doing a mess of a code, but CS50's AI hinted a data-driven menu, which I didn't get the gist of it initially. But after messing around with my code I came up with routing functions, which decide which function to call based on what the user chose. To know what option the user chose, I matched each user option to an ID (1, 2, 3...), and when the user inputed an option id, using menu_option_matcher, I matched the user input to a dictionary from the list of dictionaries defining the available menu options, which then was routed through with route_main_action() for the main menu, and route_calculator_options() for the financial calculator submenu.
